# 检索排名的影响因素

## search.py 会影响检索结果吗？

**不会影响排序，只影响"展示"。**

排名（谁排第一）完全不由它决定。真正决定排名的链条是：

```
bge-small 模型（把问题和块都变成向量）
        ↓
ChromaDB（算余弦相似度、排序、返回 Top-K）
```

`search.py` 在这条链的**下游**，只做两件事：

1. 调用 `vectorstore.py` 的 `search()`，把 ChromaDB 已经排好序的结果拿回来；
2. 去 SQLite 补充每个结果所属的**文档标题、文件名**（纯展示信息，方便看是哪个文件来的）。

它不改分数、不改顺序、不重新筛选。所以在里面加加减减，检索质量纹丝不动。

## 真正影响检索结果的环节

按影响从大到小排列，调参数/做实验时改这里才有意义：

| 环节 | 所在文件 | 影响什么 |
|------|----------|----------|
| Embedding 模型 | `vectorstore.py` 里的 `EMBEDDING_MODEL` | 语义理解能力的上限 |
| 切块大小/重叠 | `config.py` 的 `CHUNK_SIZE / CHUNK_OVERLAP` | 每个块里"装了什么内容" |
| 解析质量 | `wisnote/parsers/` | 进库的原文干不干净 |
| 相似度度量 | `vectorstore.py` 的 `hnsw:space="cosine"` | 怎么比"像不像" |
| 返回条数 | `config.py` 的 `SEARCH_TOP_K`（默认5） | 只影响看几条，不影响谁排前面 |

## 附：三个角色的分工

| 角色 | 是谁 | 干什么 |
|------|------|--------|
| 翻译官 | `bge-small-zh-v1.5`（sentence-transformers + torch 运行） | 把中文变成 512 维向量，意思相近方向相近，约100MB，CPU毫秒级 |
| 仓库管理员 | ChromaDB | 存块向量；提问时算余弦相似度并排序，返回 Top-K |
| 调度员 | `wisnote/search.py` | 调用上面两位，取 Top-5，附上标题/页码/段落等溯源信息 |

> Qwen3-1.7B 不参与检索，只负责第4阶段"读检索到的笔记片段，组织成人话回答"。
> 先找（bge + ChromaDB），后答（Qwen），找的过程不受大模型幻觉影响——这就是 RAG 的核心。
