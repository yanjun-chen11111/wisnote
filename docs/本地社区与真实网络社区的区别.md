# 本地多账号模拟社区 vs 真实网络社区

## 核心区别：数据在哪、谁能访问

| 维度 | 真实网络社区（知乎/CSDN） | 本项目本地模拟社区 |
|---|---|---|
| 数据存储 | 云端服务器数据库 | 本机 `data/wisnote.db` + `data/chroma/` |
| 访问方式 | 跨设备、跨网络（手机/异地电脑） | 仅本机 `localhost:8501` |
| 其他用户 | 真实远程用户 | 本机注册的多个账号 |
| 同步方式 | 网络实时同步 | 同一硬盘，天然同步 |
| 服务器 | 必需（云主机/部署） | 不需要 |
| 并发 | 多用户同时在线 | 单机单进程 |
| 分享范围 | 全网 | 本机内 |

**一句话**：真实社区 = 数据在网上、大家远程访问；本项目 = 数据在本机硬盘、多账号读同一份文件。
功能流程完整可跑，但**不具备跨设备、跨网络属性**。

## 为什么只能是模拟（架构决定，非缺陷）

本项目定位"纯 CPU 本地部署、保护隐私"：
- 模型运行在本机 Ollama，不联网；
- 数据是本地 SQLite 文件；
- 向量库是本地 ChromaDB 文件夹。

三者均不具备网络服务能力。**隐私不出本机（卖点）与跨设备网络社区本身就互斥**。

## 论文写法（别吹牛）

❌ 错误写法："实现了社区功能，用户可跨设备分享笔记、在线互动。"

✅ 推荐写法：
> 在单机本地环境下，通过**本地多用户机制**模拟社区交互，完整验证了笔记分享、社区检索、
> 点赞收藏、社区问答（AI 初步回答 + 人工补充）以及学习小组共享资料库等功能流程。
> 系统已按 `user_id` 做好用户隔离，并设有独立的社区向量集合；若部署至服务器，
> 仅需将本地 SQLite/ChromaDB 替换为服务端数据库并增加 Web API 层，
> **业务逻辑代码无需改动即可平滑迁移为真实网络社区**。

## 答辩预案

**问**："你的社区别人怎么用？"
**答**：
> 当前版本为本地单机部署，社区模块以本地多账号方式验证了完整业务流程。
> 系统与模型均运行在本机（这是隐私保护的设计取舍），要实现跨设备访问需增加服务端部署层；
> 数据层已按用户隔离设计，迁移时业务代码不用改。这是下一步工作。

坦承 + 给出演进路径 = 加分；硬吹 = 扣分。

## 若真要做成网络社区的代价

FastAPI 包装核心库（1~2 周）+ 数据库换 PostgreSQL + 服务器部署 + 前端改为网页。
相当于重做一层，毕设阶段不建议现在做。
