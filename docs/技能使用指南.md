# 技能使用指南：engineering-coach 与 test-pilot

## 总览

本仓库内置两个 CodeBuddy 技能，覆盖「从想法到可验证代码」的完整流程：

- **engineering-coach（工程教练）**：需求 / 想法阶段，把非工程化诉求翻译成工程问题、讲清取舍、锚定业界做法。
- **test-pilot（工程级测试）**：实现 / 验证阶段，按规格推导测试用例、用五大设计技术 + 分层覆盖、自适应项目框架、强制自检漏测。

**协作顺序**：先用 engineering-coach 把需求聊清楚、定方案；再用 test-pilot 把功能测到位。

---

## 1. engineering-coach（工程教练）

### 何时用

- 你用大白话描述想要什么 / 担心出什么问题（「刷新别掉线但要关浏览器重登」「怕截图泄露账号」）。
- 你不确定某诉求在真实开发中是否典型、成熟团队怎么解。
- 你希望 AI 当经验更丰富的导师，先对齐需求再动手，而不是照单全收。

### 工作流

1. **意图翻译**：把诉求映射到正确的工程概念（会话管理、鉴权、并发、数据隔离等）。
2. **找真正矛盾**：先点出底层技术张力（如「浏览器存储是浏览器级还是标签页级」），而不是照字面硬写。
3. **给 2-3 个标准方案 + 对照表式取舍**（刷新 / 关页面 / 地址栏 / 性能等维度），让你选。
4. **做不到就直说**：为什么做不到、业界如何妥协，不硬凑带隐藏 bug 的版本。
5. **锚定真实公司实践**：该问题典型吗 + 成熟团队 / 开源怎么解 + 该落地成什么。

### 立场（重要）

- **需求先行、代码后做**：动手前先把需求聊清楚。
- **不是命令执行者**：对薄弱 / 自相矛盾的需求会质疑、给专业判断、该说「不」就说。
- **主动拓宽视野**：主动介绍更多背景（真实团队怎么做、常踩什么坑、替代路径、什么叫生产级）。

### 反返工规则

- **冲突早停**：发现需求互相矛盾立即停手，一轮内讲清冲突与约束，等拍板。
- **不静默多版本实现**：一次权衡 -> 一次决策 -> 一次实现。
- **可短路**：你说「用标准做法」，我直接套业界模式不再多轮。
- **以「对不对」衡量，不以「炫不炫」衡量**。

详见 `references/examples.md`（含登录令牌踩坑复盘）。

## 2. test-pilot（工程级测试）

### 何时用

- 你实现完功能说「测试一下」/「怎么验证」/「加测试」。
- 你要求「工程级」「真正的」测试，而不是随手写几个 happy path。
- 我即将声明功能完成前，会自动触发自检。
- 发现 bug 想补回归测试。

### 核心原则

1. **五大测试设计技术（按场景选用）**
   - 等价类划分：输入分组，每组测一个代表（合法 / 非法类）。
   - 边界值分析：测边界与越界（min-1 / min / min+1 / max-1 / max / max+1）。
   - 决策表：多条件组合，每列一用例。
   - 状态迁移：状态对象测所有合法 / 非法转移。
   - 属性测试：断言在大量生成输入下恒成立的不变式。
2. **分层测试**：单元（函数级，快、多）/ 集成（模块间、DB / 网络边界）/ E2E（完整用户流程，少、慢）。在对的层级写对的测试。
3. **强制自检 + 漏测报告**：跑完必须列出未覆盖项（错误路径、并发、安全边界、性能）并建议补测。

### 自适应框架（不强绑 pytest）

技能会先检测项目语言与已有框架再动手：

| 语言 | 检测依据 | 首选框架 | 运行命令 |
|---|---|---|---|
| Python | requirements.txt / pyproject / *.py | pytest（或 unittest） | pytest |
| JavaScript / TypeScript | package.json | jest / vitest / mocha | npm test / vitest |
| Go | go.mod | 内置 go test | go test ./... |
| Java / Kotlin | pom.xml / build.gradle | JUnit 5 | mvn test / gradle test |
| Rust | Cargo.toml | 内置 cargo test | cargo test |
| C# | *.csproj | xUnit / NUnit | dotnet test |
| Ruby | Gemfile | RSpec / Minitest | rspec |
| Swift | Package.swift | XCTest | swift test |

规则：项目已有框架就用已有的；属性测试按语言选库（hypothesis / fast-check / jqwik ...）；沿用项目已有测试风格。

### 工作流

1. 读懂被测代码与规格（输入输出、副作用、错误、状态）。
2. 列测试类别（等价类 / 边界 / 决策组合 / 迁移 / 属性）。
3. 分派层级（单元 / 集成 / E2E，E2E 最小化）。
4. 生成带预言（具体预期结果）的用例，至少含一个失败条件用例。
5. 用检测到的框架写测试。
6. 运行并报告（通过 / 失败、覆盖类别、覆盖率、实际 vs 预期），迭代到全绿。
7. 自检 / 漏测报告（必须做）。

### 护栏

- 禁止假绿测试（永远通过的弱断言）。
- 少而精，胜过多而空。
- 没真跑过不许说「验证通过」。
- 代码不可读 / 无规格时，先说明并要澄清再写。

## 3. 安装与获取

- **项目内（克隆即自动可用）**：`.codebuddy/skills/engineering-coach/` 与 `.codebuddy/skills/test-pilot/`。
- **用户级**：复制到 `~/.codebuddy/skills/<skill>/` 即生效。
- **独立仓库（可单独分发）**：
  - engineering-coach: `github.com/yanjun-chen11111/codebuddy-engineering-coach`
  - test-pilot: `github.com/yanjun-chen11111/codebuddy-test-pilot`

---

## 4. 推荐协作节奏

1. 提需求 -> engineering-coach 翻译、找矛盾、给取舍、定方案。
2. 实现功能。
3. 收尾 -> test-pilot 生成并运行测试、出漏测报告。
4. 评审测试报告，补测或修代码，直到满意。
