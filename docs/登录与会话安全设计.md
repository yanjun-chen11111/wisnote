# 登录与会话安全设计（WisNote）

> 状态：已实现并经浏览器级 E2E 实测（2026-10-13，Playwright + Edge）。

## 当前方案：会话令牌存于会话 Cookie（浏览器级）

登录令牌由服务端签发（`secrets.token_hex(32)`，存 `sessions` 表），客户端存于浏览器**会话 Cookie**（无过期时间，浏览器关闭自动失效）：

- **写**：登录成功时经 `st.components.v1.html` 注入 JS 写 `document.cookie`（无需组件握手）
- **读**：官方 API `st.context.cookies` 同步读取（随每次页面请求带来，无异步时序问题）
- **清**：退出登录 / 吊销令牌时注入 JS 置 Cookie 过期

令牌不出现在地址栏、不写磁盘。

## 实测行为（2026-10-13 浏览器 E2E）

| 场景 | 行为 | 验证方式 |
|---|---|---|
| 登录后 Cookie 写入 | ✅ 64 位令牌写入 | E2E 实测（evaluate 检查 document.cookie） |
| **刷新页面（F5）** | ✅ **保持登录** | E2E 实测（刷新后侧栏仍显示用户名，截图存证） |
| 退出登录 | ✅ Cookie 清除并回到登录页 | E2E 实测 |
| 关闭浏览器再开 | ❌ 需重登 | 机制推断：会话 Cookie 随浏览器关闭失效（规范行为），未做关浏览器 E2E |
| 关标签页再开（浏览器未关） | ✅ 保持登录 | 机制推断：会话 Cookie 为浏览器级（非标签页级），未做专项 E2E |
| 地址栏 | ✅ 无令牌 | E2E 实测 |

## 历史教训（为什么两次返工）

1. **第一版（自建 sessionStorage 组件）**：自写 `index.html` 组件回传令牌。浏览器 E2E 实测发现：新版 Streamlit 与该组件**握手超时**（控制台 `Custom Component timeout error`），渲染事件从未送达 iframe → 令牌从未写入浏览器 → **刷新必然掉线**（该 bug 自上线即存在）。手动向 iframe 注入消息可正常写入，证明组件 JS 本身无误，是宿主协议不兼容。
2. **教训**：手写组件协议跟随 Streamlit 版本漂移而碎掉；应优先用官方 API（`st.context.cookies` 自 Streamlit 1.37 起可用）与成熟模式，而不是自己发明握手机制——这正是「模仿成熟项目」规则的来源。

## 服务端会话

- **签发**：`auth.login` 生成随机令牌写入 `sessions` 表（关联 user_id）。
- **有效期**：12 小时（`config.py` 的 `SESSION_TTL_HOURS = 12`），过期由 `purge_expired_sessions` 清理。
- **吊销**：`revoke_all_sessions` 一键下线全部设备；`logout` 销毁单个会话（E2E 实测通过）。
- **失效 Cookie 自清**：`try_restore_session` 校验 Cookie 中令牌失败时顺手清掉 Cookie，避免每次请求重复校验无效令牌。

## 多层防护

- **地址栏无令牌**：令牌只在 Cookie，防截图/历史泄露。
- **服务端有效期 + 一键吊销**：12h 过期、全量吊销止损。
- **退出即销毁**：客户端 Cookie 清除 + 服务端会话删除。
- **不写磁盘**：会话 Cookie 不落盘。

## 已知权衡

- **JS 可读 Cookie（非 HttpOnly）**：`document.cookie` 写入的 Cookie 前端可读，XSS 暴露面略大于 HttpOnly Cookie；这是 Streamlit 官方 `st.context.cookies` 只读 + JS 写入组合的固有限制。本地单机演示场景可接受；若部署公网，建议加反向代理层做 HttpOnly。
- **关标签页不失效**：会话 Cookie 是浏览器级，关单个标签页再开仍保持登录（与绝大多数网站一致）；只有关闭整个浏览器才需重登。这是与最初"关标签页即失效"诉求的取舍（标签页级存储在 Streamlit 下无可靠官方途径）。

## 公共 / 他人电脑使用场景（重要）

**风险确认**：在他人电脑登录后，若只关闭标签页而不点「退出登录」，对方重新打开标签页即处于你的账号（直到该浏览器关闭，或服务端 12h 会话过期）。这是会话 Cookie 浏览器级模型的固有行为。

**为什么不做"关标签页即失效"**：
- 该行为在 Streamlit 技术栈下无可靠官方途径（sessionStorage 需自建组件，已被 E2E 证实握手超时不可用）；
- 即使可行，浏览器也没有"关闭标签页"的服务端通知，只能靠前端心跳猜测，属脆弱方案；
- **几乎所有主流网站（Gmail、GitHub、淘宝）都是"关标签页保持登录"的行为**——这是 Web 的通用取舍，不是本项目的缺陷。

**标准对策（均按业界惯例，本系统已内置前三项）**：

| 对策 | 状态 | 说明 |
|---|---|---|
| 用完点「退出登录」 | ✅ 已内置（E2E 实测） | 清 Cookie + 销毁服务端会话；**公共电脑上的正确习惯** |
| 「吊销全部令牌」一键下线 | ✅ 已内置 | 别人即便持有你的 Cookie 也无法通过服务端校验（令牌已删，`get_user_by_token` 失败 → Cookie 自动作废清理；此条为代码逻辑推断，未做双设备 E2E） |
| 无痕/隐私窗口登录 | 浏览器自带 | 关窗口即清一切，公共电脑最省心 |
| 缩短服务端有效期 | 可配置 | 调低 `config.py` 的 `SESSION_TTL_HOURS`，越短越安全、重登越频繁 |

**使用建议**：在别人电脑上使用时，要么用无痕窗口，要么离开前点「退出登录」；若忘了退出，回家后在「账号安全」里点「吊销全部令牌」即可远程下线。


## 数据流

```
登录成功 → persist_login(token)
  ├─ html() 注入 JS：document.cookie = wisnote_token=token（会话 Cookie）
  └─ 清空地址栏参数

刷新/重开标签页 → 页面请求携带 Cookie → st.context.cookies 同步读取
  → try_restore_session 校验通过 → 保持登录

退出/吊销 → html() 注入 JS 置 Cookie 过期 + 服务端 sessions 行删除
关闭浏览器 → 会话 Cookie 自动失效 → 需重新登录
```

## 涉及模块

- `ui/app.py`：`persist_login` / `try_restore_session` / `clear_login` / `_write_token` / `_read_token`（读写清全在 Cookie 层）
- `wisnote/auth.py`：`login` / `get_user_by_token` / `purge_expired_sessions` / `revoke_all_sessions` / `logout`
- `wisnote/config.py`：`SESSION_TTL_HOURS`
- （已废弃）`ui/wisnote_cookie_component/`：自建 sessionStorage 组件，因与新版 Streamlit 握手协议不兼容已移除
